# SoundCloud without developer credentials: decision and evidence

## Decision

The default is **SoundCloud's normal website on the Mac → Mac wired audio output → one Connect/Connect:Amp RCA line-in → Sonos-managed room group**. This removes the failing SoundCloud-to-S1 encoded-stream delivery path from everyday use. It requires normal SoundCloud login, one physical audio connection, and the Mac remaining awake. It does not require developer credentials, audio-capture permission, BlackHole, a paid service, or a new network audio receiver.

This choice follows the requested priority order: playback reliability and compatibility with existing hardware outweigh eliminating a cable. It uses Sonos's native input distribution rather than assuming a continuous HTTP response will play on old firmware. **No audible result on this user's hardware has been verified in the cloud.** The user reports that all nine devices are already discovered on their Mac; we did not rediscover those devices remotely.

## The two prototypes and what was tested

### A. Native Sonos line-in routing — selected and integrated

`server/listening.ts` plus the SoundCloud page implement a persistent source/destination profile, fixed official-site browser launch on the local Mac, source availability checks, group routing, confirmation, stop, status, and explicit retry.

The source Connect need not be a destination. Selected coordinators with unselected followers are first separated; unselected rooms are not deliberately stopped or included in the new group. Room volume/mute are never raised or changed automatically. The service waits for topology convergence before source selection. It checks the coordinator's `GetMediaInfo.CurrentURI` and transport state rather than assuming a successful SOAP command proves routing. A line-in track can have no track metadata, so `GetPositionInfo.TrackURI` alone is insufficient.

Tests cover independent destinations, source outside the group, preserving volume/mute, splitting an existing group, unknown cable detection, disconnected/offline devices, partial failure, retry, concurrency rejection, delayed topology, state persistence, and stopping only the expected input. Browser tests cover desktop and iPhone-sized Chromium, including preserved legacy API access.

**Not tested:** physical cable, Mac output routing, authentic SoundCloud browser audio, actual Sonos line-in level/compression, audible output, measured delay, or synchronization of the user's speakers. Cable presence is reported only when topology supplies it; unknown is shown as unknown. Even confirmed `PLAYING` + URI does not prove sound is present.

### B. Native Mac capture + HTTP radio — experimental only

`prototypes/mac-audio/capture.swift` captures the chosen browser application's audio through ScreenCaptureKit and outputs Float32 48 kHz stereo PCM. It does not register a screen-frame output, write recordings, access SoundCloud sessions, bypass capture protection, or request capture silently. The helper filters the browser **application**, not an individual tab/profile; audio from other tabs of that browser can be included. A dedicated otherwise-idle browser is important. It requires a Mac SDK and user recording consent. **The Swift helper was not compiled or run here because this environment is Linux and has no macOS SDK.**

`radio.ts` converts PCM using an installed, verified FFmpeg executable. It emits fixed MPEG-1 Layer III frames, disables the MP3 bit reservoir for frame-aligned reconnects, retains at most 40 frames (~1 second), and discards audio older than that. A new subscriber starts at a valid recent frame. It supports close-delimited and chunked HTTP, never invents a multi-gigabyte file size, advertises no seek support, rejects nonzero ranges, limits subscribers, and drops slow consumers rather than growing memory indefinitely. Capture stalls, encoder errors, and process termination close subscribers and clean up the encoder. Restarting capture requires explicit relaunch; no automatic recording permission retries.

The terminal launcher is loopback-only unless `--lan` is supplied. LAN mode requires this Mac's private IPv4 `PUBLIC_BASE_URL`, a separate port, Host validation, rejection of browser Origin headers, and a random 256-bit per-process bearer URL. The app does not start this listener. The bearer URL grants audio access; never publish it or add it to shared screenshots.

Automated tests on Linux verified actual encoded MP3 bytes with FFmpeg decoding, both HTTP modes, live frame alignment, lack of misleading Content-Length, range rejection, subscriber limits, reconnects, bounded history, encoder absence, capture stall detection, and cleanup. These are synthetic PCM tests, not Mac capture or Sonos tests.

### Why HTTP acceptance is not hardware compatibility

A correct MP3 MIME type and an open HTTP stream do not establish Sonos live playback. A firmware can probe with HEAD or Range, expect a finite resource, buffer until a threshold, reject chunked delivery, stop after a disconnect, or handle radio URIs differently from file URIs. A listener can also be on the wrong group/stereo-pair coordinator. Infinite WAV files with fabricated lengths have finite stopping and format risks; they are not implemented as a shortcut here.

The prototype supports two real HTTP delivery modes, explicit non-seekability, continuous frames while PCM arrives, bounded startup buffering, and reconnectable frame boundaries. Receiver buffering is still controlled by the device. A radio wrapper (`x-rincon-mp3radio:`) is a hardware-test candidate, not an asserted fix; the existing application playback validation was not broadened to accept arbitrary wrapper URIs. Do not promote the prototype until long audible S1 tests, grouping, pause/resume, silence, Mac sleep, and network interruption behavior are measured. Use line-in meanwhile.

## Source audit

Direct Apple/Sonos/Chrome documentation HTTP requests returned 403 in this cloud. Public source repositories were available through the platform's Git proxy. The following files were inspected; a mirrored sample is identified as such rather than being described as a fetched Apple API reference:

- [Apple ScreenCaptureKit sample (mirror)](https://github.com/Fidetro/CapturingScreenContentInMacOS/tree/083aae150329ea6a34e8831fd137b3e1a3059e9a), `ScreenRecorder.swift`, `CaptureEngine.swift`, and README. The sample identifies its WWDC22 provenance and recording permission/restart requirement. Original [WWDC session](https://developer.apple.com/videos/play/wwdc2022/10156/) and [Apple documentation](https://developer.apple.com/documentation/screencapturekit) remain the authoritative Mac references; native compilation still needs local verification.
- [AudioCap source and notes](https://github.com/insidegui/AudioCap/tree/6f609e8ad1b1e11fa0e8edbe91864cb099f00de3), on process taps, macOS 14.4, permission, resource lifecycle, and optional private permission APIs. No code from its private-API path is used.
- [Sonos HTTP API line-in action](https://github.com/jishi/node-sonos-http-api/blob/3776f0ee2261c924c7b7204de121a38100a08ca7/lib/actions/linein.js), showing `x-rincon-stream:UUID` on the coordinator followed by Play.
- [node-sonos services](https://github.com/bencevans/node-sonos/tree/ceaa85502d4953cdec472d42664ffaf939a4104f), including AVTransport/AudioIn control and line-in example.
- [SWYH-RS README and streaming server](https://github.com/dheijl/swyh-rs/tree/14d8e13b01e4b1ebb5df0c939407d2ba487cfb85), on differing renderer formats, stream sizes, buffering/stutter, silence, coordinator selection, and unverified Mac support. Its documented current-firmware results are not S1 certification.
- [MDN getDisplayMedia documentation source](https://github.com/mdn/content/blob/main/files/en-us/web/api/mediadevices/getdisplaymedia/index.md), fetched from the public repository: audio availability depends on the chosen surface, OS, and browser; systemAudio is a hint, permission cannot be persisted, and transient user activation is required.
- [BlackHole](https://github.com/ExistentialAudio/BlackHole/tree/561d934c77a1fa64987e01ccabe890fed30e181f), on virtual loopback, Core Audio Float32, Multi-Output caveats, and licensing. No driver is installed or bundled.

For local setup consult [Sonos line-in support](https://support.sonos.com/en-us/article/use-line-in-on-sonos), [line-in settings](https://support.sonos.com/en-us/article/adjust-line-in-settings), and your exact S1 model/firmware documentation. Protected audio may be unavailable for supported capture APIs; never remove protections to make the prototype work.
